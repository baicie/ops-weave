# ADR-083：完整指标窗口与有界迟到补采

日期：2026-10-04。状态：实现；实际验收结果见验证报告§121。本决策扩展[ADR-079](079-confirmed-continuous-metric-windows.md)。

## 决策

沿用固定发布版本、Java执行器和四个启动单元。每个半开60秒窗口最多600条来源记录。读取前后核对同一item/host/key/unit/value_type；history.get使用clock/ns升序、常规limit=101。满页的最后一秒可能不完整，因此只采用之前的整秒，下一页完整重读边界秒；不能使用最后clock+1跳过同秒的纳秒点。单秒满页时，只读该秒，limit为剩余点数+1；哨兵或累计超过600条则整窗失败。

每个窗口最多20次history请求，两次元数据核对另计；整个来源读取共享20秒单调时钟预算，每次网络超时取剩余预算与10秒的较小值。超时、超限、非法顺序、重复clock/ns、错误item或任一页失败不会返回成功前缀，不写输出、不推进检查点。只证明在本次有界读取中覆盖了窗口，不声称上游提供原子快照。该边界依据[Zabbix 7.0 history.get](https://www.zabbix.com/documentation/7.0/en/manual/api/reference/history/get)的包含式秒范围与clock/ns排序。

下一个窗口到达稳定期后，先重新读取上一已确认的60秒。对相同毫秒点重新执行原固定算子和映射，用原时间戳子集核对原批次摘要；旧点消失或值改变以SOURCE_WINDOW_CHANGED暂停。不会以更晚的来源结果覆盖已确认值，也不会用空结果删除旧点。新加入且通过转换的点，以独立批次补采，reconcilesBatchId指向同租户、同所有者、同流程/系列/范围的最近完整确认批次，latePoints只计新增标准点。

补采保留完整窗口的新摘要及原时间戳，原证据不改写。先提交IN_FLIGHT，再通过既有时序适配器的写前比对跳过相同旧点，只写新增点并精确回读。确认补采增加累计点数，不增加确认窗口数、不移动游标；下一次调度才处理下一窗口。补采消耗同一次授权的批次额度与200份证明总额，不新建授权、独立线程或持久逐点任务。控制UUID重放、STOP代数检查、当前身份与pin复核保持；回看后再次复核，停止或撤权后不继续读取下一窗。

UNKNOWN补采仍绑定原完整摘要，只允许读原时序系列/时间戳核验；没有新来源读取或写入重试。完整匹配后保留停止状态，由明确RESUME恢复。毫秒碰撞仍按原规则：相同值合并并计collapsed，不同值拒绝。

V047仅将每批证明的JSON大小边界从8192提升至24576字节，支持600个时间戳及两字段补采元数据。不增加点值表，不重写既有行；旧16字段证明解码为reconcilesBatchId=null、latePoints=0。请求/状态/证明契约和Web校验同步更新。时序写入正文仍受4MiB边界限制，回读选择最多600个时间戳。

## 局限

仅回看最近一个已确认窗口，且等到下一窗口就绪才检查。最后一窗若停止、授权到期、总额耗尽或来源过期，不自动继续回看；更早的迟到数据、历史修订和跨版本迁移尚需单独的受控修复流程。全过滤的迟到来源行不会增加latePoints；该计数不是所有来源迟到行的质量统计。当前进度不代表无限分页或无限补采。

每次调度可能读取回看和当前两个窗口；它们共享执行器并发，分别受读取预算约束。当前本机租户锁、进程门禁与精确回读不等于分布式租约/fencing、跨系统原子提交、生产容量或断电耐久性验收。
