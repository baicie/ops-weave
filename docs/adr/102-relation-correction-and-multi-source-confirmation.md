# ADR-102 关系更正与多来源确认合并（设计边界）

状态：**已实施**（2026-10-10，OW-ST05 收尾切片：契约→领域→存储 V066→API→Web→测试已落地并实测；原登记的"未决"项按本页"后果与边界"记录的保守方向落地）

## 背景

第5节要求"人工创建/更正/终止关联需理由、服务端校验和幂等请求"，且"来源关系使用独立 Observation：一个来源失效不抹掉其他来源仍确认的关系"。ADR-100 覆盖终止/历史/基数，ADR-101 覆盖唯一性、终止不复活与 RELATION 输出 PENDING。仍缺两块语义：

1. **关系更正**：改一条既有关系实例的端点或关系类型。ADR-101 明确"重新建立属于将来的更正/新版本流程，不通过重复创建绕过"，因此更正必须是独立显式流程，而非重复 create。
2. **多来源确认合并**：同一对端点、同一关系类型下的单一实例记录上，多个来源各自确认；单一来源失效不应抹掉其他来源仍确认的结论。

本决策登记这两块的设计与边界；外部链接登记入口（解决 PENDING 端点解析）已另行实施。

## 决策

### 1. 关系更正 = 显式更正记录，不走重复创建

- **更正是一等命令**（如 `POST .../relations/{relationId}/correct`），携带 `requestId` 幂等键、`expectedVersion` 对象版本 CAS、更正理由（1–256 无控制字符），以及要改的端点/类型新值。命令在写事务内检查类型方向、两端类型与基数（沿用 ADR-100 决策 4）。
- **保留原历史与理由**：更正不删除、不覆盖原关系行，而是写有效结束时间（或追加撤销/更正记录）后建立新值，原端点/类型、原理由、原来源标注在历史中可追溯。禁止把更正做成"原地改写"以致丢失原断言。
- **幂等**：同 `requestId` 同内容重放返回原回执；同键异内容 409。更正使用独立幂等键，不复用创建键。
- **不走重复创建**：ADR-101 的唯一性（同端点同类型仅一条）与"终止不复活"仍成立。更正因为携带 `relationId` + `expectedVersion` 且走专用命令，不会被误判为重复 create；对已终止关系的更正要么明确拒绝，要么作为显式新版本流程处理（须另行决定，未决）。
- **冲突可见**：更正遇到版本失配、越权端点、非法类型时显式 409/403/400，不静默获胜，不改写人工断言。

### 2. 多来源确认合并 = 单实例记录上的多确认语义

- **单实例记录、多确认**：一对端点在同关系类型下仍只有一条实例记录（ADR-101 决策 1）。多个来源对这条记录的确认作为独立、可追溯的确认条目挂在记录上（每条带来源标识、确认时间、dataMode），而不是各自创建关系实例。
- **单一来源失效不抹掉其他来源确认**：一个来源失效（其 Observation/批次撤销或来源下线）只撤回该来源自己的确认；只要还有其他来源（或人工断言）仍确认，关系记录保持有效。只有当全部来源确认与人工断言都撤回时，才按终止流程写有效结束时间并保留历史。
- **人工与来源并列、不互相覆盖**：人工断言是一条独立确认，不改写来源原文；来源确认也不覆盖人工断言。冲突要可见、有明确策略，禁止最后写入者静默获胜（沿用 ADR-101 决策 3）。
- **确定性与幂等**：每个来源确认有确定性幂等键（来源身份 + 批次/执行标识派生），跨执行重放不重复计数；来源失败不删除既有关系或既有确认（沿用 ADR-101 来源失败不误删除）。

## 后果与边界

- **已实施（2026-10-10，OW-ST05 收尾切片）**：更正命令 `POST .../relations/{relationId}/correct`（回执 `entity-relation-correction-receipt`）与更正记录只读分页（`entity-relation-correction-record/-page`、`GET .../relations/corrections`）；确认命令 `POST .../relations/{relationId}/confirmations`、失效撤回 `POST .../relations/{relationId}/confirmations/withdraw` 与确认视图 `GET .../relations/{relationId}/confirmations`（`entity-relation-confirmation-command/-withdraw-command/-receipt/-entry/-view`）。全部新增闭合 Schema 并登记 OpenAPI（挂 clientRequestId，错误码闭合 400/401/403/404/409/503，请求不接受 tenant/actor）。存储迁移 **V066**：`entity_relation_correction`（原记录→更正后记录、理由、expectedVersion、更正时间；`(tenant,request_id)` 幂等主键、原记录唯一关联）与 `entity_relation_confirmation`（`(tenant,relation,来源类别,来源标识,批次标识)` 确定性条目主键；确认/撤回请求各有唯一幂等索引；条目只标记撤回、永不删除）。内存实现同语义。Web 关系实例页/详情抽屉提供更正表单与多来源确认视图（含登记/撤回表单），沿用未知结果原样重试与身份切换清理。
- **更正语义落地选择**：写事务内先按 `requestId` 做重放判定、再做状态与版本 CAS（沿用 ADR-100"重放不被已终止预判误拒"的教训）；原记录只写有效结束时间与更正理由（版本+1、`close_request_id` 保持空），保留其端点、类型、来源标注与历史，更正记录显式关联原记录与更正后记录，不做原地改写。更正后的新实例沿用"创建幂等键=实例 id"，更正使用独立幂等键（同键同内容重放原回执、同键异内容 409）。更正后的取值不得撞任何既有（含已终止）同端点同类型记录——旧占位不因更正释放，唯一性与终止不复活不放宽。
- **原"未决"项按保守方向落地**：①更正已终止关系**明确拒绝**（409 `RELATION_CORRECTION_CONFLICT`），不做显式新版本复活，与"本决策不放宽任何一条"一致；②多来源确认条目挂在单条实例记录上、从不创建实例，因此**不参与基数计数**（基数仍只计 `valid_to IS NULL` 的关系行）；③撤回以撤回时刻写有效结束时间并保留历史，人工终止（close）保持独立显式命令与理由留存，两者竞态在同一写事务内串行判定、不静默覆盖。重复撤回幂等返回首次记录（首次理由不被后来者改写），同 `requestId` 异内容 409；每条关系最多 50 条确认条目（数量预算，超出显式 409）。
- **冲突可见**：更正冲突统一 409 `RELATION_CORRECTION_CONFLICT`、确认冲突统一 409 `RELATION_CONFIRMATION_CONFLICT`（重复/复活、已撤回条目再确认、条目内容冲突、容量、版本失配等），非法输入 400、越权 403、缺失 404、存储不可用 503；不引入最后写入者获胜，来源失效不删除关系或既有确认条目，人工断言与来源确认条目互不改写。
- **边界**：来源确认/失效目前经受控平台 API 显式登记；工作流 RELATION 输出写入仍按 ADR-101 直接写实例并以 `sourceRef` 标注来源，重复/复活仍显式 409 失败关闭，不因多确认语义放宽。确认视图展示的来源标识是确认命令中显式断言的内容，关系行 `sourceRef` 仍只留服务端。多实例联测与真实环境验收未做。
- 与 ADR-100/101 一致：终止不复活、唯一性、失败关闭、历史保留继续适用；本决策不放宽任何一条。
