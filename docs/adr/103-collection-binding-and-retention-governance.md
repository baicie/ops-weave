# ADR-103：采集绑定与留存治理（发布≠启用、清理必须显式）

状态：**已实施**（本切片）。证据见 [VALIDATION-REPORT §180](../VALIDATION-REPORT.md)，
契约见 [治理契约](../../contracts/governance.md)。备份/恢复/WAL 擦除仍属未实施（ADR-048）。

## 问题

发布一个不可变工作流版本之后，平台此前缺少一个明确的对象来回答：
「这个来源实例的采集批次，到底允不允许被这个已发布版本消费？」
运行时任务启停（`WorkflowRuntimeControl`）只回答「这个 owner 的任务跑不跑」，不回答「这个版本
是否被授权绑定到这个来源」。同时，接入/确认/登记回执只增不减，ADR-048 只记录了留存边界而没有
清理入口，运维也没有受权删除一个明确可清理对象的通道。

## 决定

1. **发布 ≠ 自动采集绑定。** 绑定是独立对象（`workflow_collection_binding`），只由显式
   `enable`/`disable` 命令产生，命令要求显式授权、幂等 requestId 与理由，回执不可变且可原样重读。
   启用/解绑都不启动采集、不写实体、不调用模型。
2. **绑定是消费门禁，不是开关。** 只有 `BOUND` 且版本 pin（workflowId/revision/digest）与来源实例
   完全一致时，受控批次消费（`/runtime/execute` 携带来源批次、`tick`、Host 批次）才被允许；
   否则 `COLLECTION_BINDING_REQUIRED` 失败停止，任务转 FAILED 且不再读取来源。解绑即时停止消费。
   显式手工样本执行是用户输入，不是采集，不需要绑定。
3. **绑定与任务生命周期是两个对象。** 不重复 `WorkflowRuntimeControl` 的 start/stop 语义；
   本切片也不做多版本并行消费——切换绑定会让旧版本的消费立即停止（失败停止），
   这比"旧版本跑到结束"更严格，也与「解绑即时停止消费」一致。
4. **回执留存沿用扫描运行预算的形状，但不沿用它的清扫时机。** 每范围上限（默认 1000/租户 5000）
   可见、受保护记录永不删除、读取不清理、**打开扫描时不清除**、默认不自动删除。清理是
   预览 → 人工确认 → 带计数回执，确认必须带回 `previewDigest`，候选集变化即冲突而不是扩大删除。
   受保护规则按类型固定：接入回执被来源实例引用即受保护，命令/登记回执的当前最新一份受保护，
   其余为被取代的历史回执。
5. **运维删除只做软删除且拒绝受保护目标。** `entity.manage` + 理由必填 + 幂等 requestId + 审计计数；
   目标仍是当前关系端点即 409，不删除；实体行保留，因此旧 Incident/Evidence 引用不被级联破坏
   （设计 §5 语义）。物理擦除不承诺（ADR-048 决定 5）。
