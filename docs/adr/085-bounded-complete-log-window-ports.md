# ADR-085：完整有界日志窗口端口

状态：接受；来源、纯处理和存储端口已实现，持续任务控制与持久检查点继续。

## 背景

最新5条样本不足以表示完整日志窗口。按5条拆成多次存储尝试时，进程中断会丢失尚未尝试的内存正文；把正文放进平台PG或逐条持久编排不符合遥测分链路边界。

## 决定

- 在既有Java平台模块增加60秒半开窗口读取，等待10秒，最近24小时内，每窗最多1,000条、20次历史请求和20秒总来源预算。读前后核对固定LOG项的Host、完整键、单位和类型。分页按clock/ns升序，满页重读整个边界秒；过量、异常、重复、乱序、漂移、字节/时间预算失败均不返回成功前缀。
- 来源接收时间的完整纳秒位置与映射后的eventTime分开。一个已固定来源项中的clock/ns是采集位置，原始eventId不视为全局唯一ID。稳定位置及输入/输出摘要供后续持久证明使用；当前端口不提供跨请求自动去重或任务检查点。
- 既有固定算子每5条在内存中处理，但只有整窗全部验证完成才生成批次；允许显式FILTER，保留原输入索引。任何REJECTED使整窗失败。空/全过滤窗由未来任务元数据确认，存储端口拒绝空POST。
- 增加内部`WorkflowLogWindowSink`，整窗一次有界JSONEachRow POST，随后可按可信tenant/owner/request/workflow/version/digest读取。存储尝试后异常保守为未知；端口本身不重试。回读须核对索引、纳秒位置、原文、可选缺失值及摘要，行数不能替代确认。
- 在既有日志数据库部署V002表`workflow_log_windows`，UInt32索引和独立source_position。实际25.8.33.6专属小表探针拒绝修改旧样本表排序键UInt8→UInt32（Code 524），因此不修改旧样本数据/键。新表排序键按原批次和索引去重；这不代表跨批次或跨故障exactly-once。日志数据仅在内存及日志库，未增加PG正文表或新数据库。
- 抽出包内有界HTTP适配器，复用于旧样本和新窗口；旧样本仍为5条/64KiB，新窗口最多1,000条/8MiB。固定loopback、无代理/重定向、密钥仅请求头，应用账号只获固定表SELECT/INSERT，不在业务请求执行DDL。

## 后续边界

当前没有新增公开HTTP写入接口、后台轮询或Web连续日志入口。下一阶段需先提交不可变窗口证明，再做一次输出、精确回读、确认后推进检查点；补齐原UUID、代数停止、短时委托、未知只读恢复及迟到补采去重。部署与验收仍沿用四启动单元；生产容量、HA、长期保留和S7继续。

来源分页不是提供者事务快照；元数据前后匹配不能证明历史行在读取期间不变。迟到行和历史修订须由后续固定窗口回看/摘要对照处理，不以两次元数据查询宣称源数据快照隔离。
